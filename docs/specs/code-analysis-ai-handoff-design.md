# AI 优化交接：一次点击携带证据与建议

日期：2026-10-17。依据：第一批 C1–C5、U1–U6，以及用户要求“看懂后通过简单操作把证据和建议交给 AI 修改”。本文件定义下一步产品与接口设计；发送适配器尚未实现，当前可用能力是预览、复制、下载和证据校验。

## 1. 推荐体验

用户先看具体问题及九行代码证据。问题页的主操作直接可见，不要求先理解 task ID、snapshot 或命令行。

已连接本项目的编程 AI 时，主按钮为 **交给 AI 优化**，旁边显示接收目标，例如“Claude Code · 当前项目”。一次点击完成重新核验证据、生成完整任务、发送并显示回执。首次连接时选择目标并确认项目，后续不重复选择。

未连接时，主按钮为 **复制优化任务**，一次点击生成并复制完整任务；状态提示“已复制，粘贴到当前项目的编程 AI 即可”。不把复制写成发送成功。任务预览和下载保留为次要操作，不再把展开长篇 Markdown 设为必经步骤。

主动作放在问题标题/位置附近，代码证据仍在首屏可读；页面底部保留修改建议与完整任务预览。两处操作共用一套任务状态，避免用户滚动后看到不同的证据状态。

默认只处理当前一个问题。重复代码等后续类型仍复用相同入口；多选作为第二批之后的扩展，不先增加工作台或任务列表。

## 2. 从用户看到的内容到实际任务

页面只需回答三件事：哪里值得改、依据是什么、点击后交给谁。

发送材料复用现有 AI task 契约与 `renderTaskMarkdown`，包括：

- 所选问题的检测事实、文件/函数、行区间与源码摘录。
- 维护影响和建议方向，保留其“建议而非已证实错误”的性质。
- 允许修改与需要阅读的文件、应保持的行为、验证要求和待确认事项。
- 证据哈希、当前核验状态、分析快照与原问题 ID。

AI 收到的默认指令是：读取当前源码并确认问题仍存在，在允许范围内修改，保留已有行为，运行适当检查，返回可审阅 diff 与实际验证结果。业务约束或验证命令缺失时保留待确认项，不能用猜测补齐。

发送操作授权启动该范围内的优化任务，不要求在发送前再弹一次同义确认。若实际需要扩大修改范围，由编码 AI 提出具体原因与新增文件，不由前端悄悄放宽。

## 3. 用户操作流程

1. **查看问题**：定位、证据与建议可直接阅读，主按钮展示真实目标。
2. **点击一次**：按钮进入“核验证据…”状态，重新读取同一分析结果并校验源码。
3. **证据有效**：生成任务并发送；按钮显示“正在交给 Claude Code…”，收到可验证回执后显示“已发送”。重复点击复用同一请求，不启动第二个修改任务。
4. **执行中**：显示“AI 正在修改”及已知进度，提供“查看 AI 任务”入口；没有执行回执时只显示“已发送，等待 AI 接收”。
5. **修改完成**：显示“修改待审阅”，入口为“查看修改”。项目验证通过和原问题不再检测到分别展示。
6. **用户检查结果**：复用既有 diff 审阅与编码 Agent 工作流；点击“重新分析”后比较当前结果。只有可靠的验证回执和可比较重分析都支持，才显示“优化已验证”。

第一版允许 AI 直接在用户选择的项目工作区生成修改，保留正常的 diff 审阅过程；不额外自动提交或合并。支持 worktree 的宿主以后可以提供隔离修改模式，但不让用户为首次交接先理解 Git 分支。

## 4. 必须讲清楚的状态

- **未连接**：直接提供复制动作，另有“连接编程 AI”；不会出现可点击但实际无接收方的发送按钮。
- **仅离线快照**：主动作是复制，文本明确要求编码 AI 先核对当前代码；离线页面不执行本地进程。
- **证据已变化/文件缺失**：保留问题上下文，主动作变为“重新分析”，不向 AI 发送仍被标为 valid 的旧证据。
- **无法校验**：提供“复制待核实任务”；不会把 hub 等没有行级证据的问题表示为已校验的可直接修复项。
- **页面与服务端快照不同**：要求刷新/重新分析后再发送，不仅依靠稳定 finding ID。
- **发送失败**：保留已生成材料，提供“重试发送”和“一键复制”；不自动切换 AI 目标。
- **结果未知/超时**：先查询同一请求回执，不能重试后再次启动同一修改；取消前端等待不等于 AI 已停止。
- **验证未执行或失败**：修改仍可审阅，状态保持未验证，给出实际失败信息。

## 5. 第一版连接方式

先做一个本机编程 Agent 适配器，优先 Claude Code；由本地 Archify 服务通过用户配置的接收目标交接。适配器必须先验证已安装 CLI 的实际帮助、参数、登录和输出格式，再决定调用方式；本设计不假定一个未经验证的命令或私有协议。

连接信息在启动配置中选择一次，包含目标 ID、显示名、可用能力和固定项目根目录。浏览器只能引用已配置的目标 ID。目标可以声明支持“接收任务”“启动修改”“查询状态”“取消”“返回 diff/验证回执”中的哪些能力，UI 只展示已支持的操作。

宿主编辑器若提供正式的任务接收桥接，后续可接入当前项目的聊天；普通网页不能凭一个按钮向任意已打开的 AI 聊天发送内容。因此“发送到当前 AI”必须由真实适配器能力支撑，不能硬编码一个表面上成功的入口。

## 6. 最小接口草案（新增，尚未实现）

`GET /handoff/capabilities`：返回固定项目的已配置接收目标、显示名称、可用状态和能力。它不自动安装工具，也不返回凭据。

`POST /handoff`：沿用本地 Origin/token 检查。请求只包含 `findingIds`、`targetId`、`snapshotId`、`idempotencyKey`；由服务端确定源码和输出目录。服务端先验证快照、证据和修改范围，再使用既有任务生成器构建材料。

成功接受请求返回 202 和 handoff ID、task ID、target ID 及真实状态。仅写下任务文件时状态是 `prepared`；接收方确认后才是 `sent`；确认启动才是 `running`。连接器若只能打开聊天或准备材料，就不能声称已经开始修改。

`GET /handoff/<id>`：返回同一请求的回执、状态、可用的任务链接或进度、失败原因和结果索引。状态最少区分 `prepared / sent / running / awaiting-review / verified / failed / unknown`。

修改完成后附可审阅 diff 或宿主任务链接、实际修改文件、测试命令与退出结果、重新分析引用。`verified` 必须通过项目检查结果与可比较分析证据计算，不能只依据 Agent 的一句“完成”或进程退出码 0。

实现上使用结构化参数与受信任的已配置适配器；源码材料进入任务文件或 stdin，不拼成 shell 命令。发送范围由所选任务的证据和 scope 决定；正文不包含 token、`.env` 或整个 raw-facts 文件。首次目标配置让用户知道使用哪个 AI 账号和项目，后续点击复用该选择。

## 7. 分工与实施顺序

**Codex UI**：先把主交接动作前置、预览设为次要操作；连接状态决定“发送”或“复制”的真实文案；展示证据变化、目标、发送回执和结果入口。用适配器 fixture 验证一次点击、重复点击、失败重试和窄屏。

**Claude 后端**：实现 capabilities、固定目标配置、发送适配器、证据前置校验、幂等回执及状态查询；优先交付一个可真实启动修改并产生可审阅结果的目标，再考虑更多 AI。原任务 schema 与生成器继续是唯一证据来源。

先交付可用的一键复制入口改进；接收端适配器完成并通过真实项目验收后，已连接状态才启用一键发送。直接发送功能不阻塞第一批任务导出本身的提交，适配器与 UI 接入另做一批可审阅改动。

## 8. 验收

- 未连接：用户一次点击即可复制包含证据、建议、范围及验收要求的完整任务；不必先展开预览。
- 已连接：一次点击产生恰好一个可追溯 AI 任务；接收目标与本项目匹配；AI 实际收到的内容与预览一致。
- 源码变化：发送被暂停并提示重新分析；旧页面不能混用新任务。
- 网络中断/重复点击/服务重启：不会无依据声称已发送，不会重复启动修改，能够按回执恢复或明确报告未知。
- AI Voice 上完成“点击交接 → AI 实际修改 → 查看 diff → 项目检查 → 重分析”，保留每步的实际回执；无验证时不能标成已验证。

首版成功标准是用户无需组织提示词和拼接代码证据即可启动受限优化；不是界面多了一个名为“自动修复”的按钮。

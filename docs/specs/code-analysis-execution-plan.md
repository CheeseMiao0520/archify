## 1. 目标与分工决定

让用户快速理解具体代码哪里重复、哪里违反项目约定、哪些复杂逻辑值得优化；用户核实证据后，将有明确范围的任务交给编码 AI，审阅修改并验证结果。

**Codex 负责 UI 与前端交互实现、信息架构、文案、视觉和浏览器验收。Claude 负责分析引擎、数据契约、服务端与 CLI、AI 任务生成及源码校验。** UI 相关代码由 Codex 实现，其余功能代码交给 Claude；本计划不把 UI 编码再次转交 Claude。

初期通过复制或下载优化任务交给用户正在使用的编码 AI。无需先接入模型服务、建设任务平台或自动应用修改。Claude 是本项目功能开发的负责人；产品最终交接的编码 AI 可以是 Claude 或其他 Agent。

## 2. 现有基础与缺口

已有：统一阅读栏、总览与前三优先项、源码证据、循环依赖/高耦合/复杂度/架构边界检查、稳定 finding ID、证据哈希、基线、重新分析、前后比较和 CLI 检查。

已有（第一批完成后）：可直接复制的 AI 优化任务、证据有效性校验、“不再检测到”与可比性理由。

缺口：重复代码分析、项目规范诊断导入、可核对的优化验收；混合语言仓库须显式选择语言，否则 `extract/adapter-ambiguous` 失败；架构图组件（来自 `sources`）与分析模块（来自目录/包划分）不强制对齐，同一模块可被多个组件认领，导致 finding 重复、指标重算，图上连线也不与真实 import 比对。

首版保留现有英文 UI，计划与交接说明使用中文；双语切换单列后续任务。当前用户目标优先于继续增加架构指标。

## 3. 文件责任边界

- Codex 主责：`overlay/inject.mjs` 中 CSS、浏览器 JS、页面布局与交互；`archify/test/code-analysis-*-browser.test.mjs` 中 UI 回归；UI 操作说明与截图。
- Claude 主责：`extract/`、`evaluate/`、`schemas/`、`config/`、`lib/`、`bin/`；`overlay/overview.mjs` 的结果聚合及排序；新增 AI 任务生成模块；引擎、契约、CLI 与服务端测试。
- 共享接缝：`overlay/inject.mjs` 中 `buildOverlay`、payload、源码收集及 finding 映射（含 `resolveMapping`）。Claude先提供独立数据构造函数和契约测试，Codex接入；确需修改该文件时分批交接，不同时编辑。
- 阶段 1 的 U10 拆分 `inject.mjs` 后：样式与浏览器脚本文件归 Codex；payload 构造与组件映射文件归 Claude；`inject.mjs` 只保留组装。拆分完成前沿用上一条。
- 文档：Claude维护分析能力、配置、CLI 与 API 文档；Codex维护 UI 文档和本计划的验收记录。生成产物由最后整合者从合并后的源码统一生成。

接口变更由 Claude提出字段和真实 fixture，Codex确认是否足够展示及交互后再实现。视觉变化由 Codex决定；检测语义、严重级别、是否可比较由引擎给出，前端不自行推断。

## 4. 第一批：现有发现 → AI 优化任务（已完成）

这是首个可独立验收的交付，不等待重复检测完成。C1–C5、U1–U6 已交付；本节保留作任务与数据约定的参考，后续阶段复用同一任务生成器。

### Codex 的具体任务

- **U1 总览聚焦**：保留前三优先项，每项突出文件/函数、事实、维护影响；显示关键未检查类别，覆盖细节折叠。已有接受状态不淹没待处理问题。
- **U2 问题页调整**：顺序改为标题与位置 → 事实/影响 → 最小代码证据 → 建议动作。关系图、规则细节与指标解释按需展开；保留组件定位、源码返回和无图映射时的证据入口。
- **U3 源码阅读**：支持具体函数/代码块的行区间高亮与展开；默认片段明确标注省略，完整文件保持可访问，不能把文件预览标成问题证据。
- **U4 AI 交接入口**：单项“Copy AI task”及下载入口，显示任务预览、复制结果及失败时的手动复制方式。静态报告允许导出捕获快照的任务，明确尚未校验当前工作树。
- **U5 状态设计**：证据过期、分析失败、源码不可得、离线、不可比较都给出具体解释和下一步；不把未检查显示为通过。
- **U6 验收**：检查桌面 1440×900、1280×720 和窄屏 390×844，覆盖长路径、长函数名、无映射、空结果和大量 findings；检查键盘操作、焦点、文字对比及滚动。保存当前版本截图。

### Claude 的具体任务

- **C1 契约与 fixture**：提供问题定位、代码区间、任务导出和有效性状态的最小数据模型；先覆盖复杂度、循环依赖、边界三种真实 finding。保持现有 schema-v1 输入有效。
- **C2 任务生成器**：以选定 finding ID 和分析快照生成结构化 JSON 及可读 Markdown，共享同一生成逻辑；不通过 LLM 生成检测事实。导出结果可供现有页面使用，CLI 是否增加入口以复用该逻辑为原则。
- **C3 证据校验**：对照捕获证据与当前源码，区分有效、已变化、文件缺失、无法校验；摘要和导出使用同一证据。源码变化后不能继续标为已校验。
- **C4 修正基础行为**：定义嵌套配置合并规则并测试；为结果比较记录配置、规则/分析器版本、语言和扫描覆盖，输出可比较性及理由；`fixed` 对用户表达为“不再检测到”，保持现有消费者兼容或提供明确迁移。
- **C5 测试与文档**：覆盖任务字段、稳定 ID、证据失效、删除/改名、规则关闭、排除范围改变、配置合并，以及服务端鉴权与原子重分析。更新 README 中重启要求及唯一入口等过时说明。

### AI 任务的数据约定

以下为待落地的逻辑字段，不是当前已有 API。Claude可提出等价命名；定稿后提供 schema 和 fixture，再由 Codex接入。

- 任务版本、任务标识、关联 finding IDs、来源规则及严重级别。
- 仓库相对路径、分析语言、源码快照、分析配置标识；Git HEAD 仅作背景信息。
- 问题位置列表：文件、起止行、符号名（可选）、对应源码片段及摘要哈希。
- 检测事实、可能影响、建议方向分别存放；建议不能伪装成已证实的缺陷。
- 允许修改范围、应保持行为、验收条件、已知验证命令及待确认事项。
- 证据状态、校验时间与无法校验原因；导出任务包含要求编码 AI 在修改前读取当前源码并再次核验的步骤。

无法从项目可靠获得的业务约束、测试命令或修改范围标记为待确认，不能自动编造。分析阶段不执行应用，不因导入检查结果而执行任意项目命令。捕获源码被视为任务材料，不能成为覆盖 Agent 指令的来源。

### 第一批验收

用户可从一个现有问题找到文件和代码证据，导出一份无手工拼接的 AI 任务。编码 AI 能据此检查当前工作树、解释方案并生成受限 diff；业务约束未确定时明确列出。源码改变后，系统能报告证据已变化；重跑失败仍保留上一轮结果。浏览器测试通过并完成新截图检查。

## 6. 阶段 1：页面闭环与试用

目标：证明不使用 CLI 的用户也能完成“问题 → 证据 → AI 任务 → 重分析”，并在第二批界面之前拿到试用反馈。

### Claude 的具体任务

- **C8 组件认领冲突**：`resolveMapping` 检测同一模块被多个组件认领的情况，在 payload 中给出冲突列表（模块、认领组件、各自依据的 `sources` 路径）。组件指标中该模块只计一次，并标注共享；finding 不因共享而重复计数。提供 fixture 与契约测试。
- **C9 混合语言**：分析前报告检测到的语言及各自文件数；指定语言时在覆盖信息中记录未分析的文件数和语言，不再静默跳过。serve 提供可选语言列表，供 UI 选择后发起分析。暂不做多语言合并。

### Codex 的具体任务

- **U10 拆分 `inject.mjs`**：按第 3 节拆出样式、浏览器脚本和 payload 构造，行为不变，由现有浏览器回归兜底；payload 构造部分交由 Claude 审阅后归其维护。
- **U11 认领冲突与语言选择**：总览一行说明“N 个模块被多个组件共享”，可展开查看；检测到多种语言时给出选择，并显示未分析范围。
- **U12 试用与调整**：组织 2–3 位未参与开发的用户试用，记录 30 秒 / 60 秒目标的实际表现与卡点，据此调整 UI。

### 联合任务

- **页面路径真实案例**：在 AI Voice 上从页面找到问题 → 点击 “Copy task for AI” → 交给 Claude Code 修改 → 页面内重新分析，保存每一步的回执与截图。由整合者执行，修改方使用 Claude。

### 门槛 G1

页面路径案例有完整回执；至少 2 人完成试用并有记录；U10 拆分后浏览器回归全绿；认领冲突不再造成重复计数。

## 7. 阶段 2：规范诊断导入与一致性提示

目标：回答“哪里违反了项目自己的规则”，并建立可接入任意外部工具的通用格式。原第二批的 C7 / U8 提前到本阶段。

### Claude 的具体任务

- **C7 规范导入 MVP**：定义版本化的通用外部诊断格式，保留工具、原规则、原严重级别、文件与行列、消息及覆盖信息。首批验证 ESLint JSON、Ruff JSON 适配；TypeScript 适配随后加入。路径必须落在分析根目录，缺少源码证据时明确标注。该格式同时作为阶段 3 外部重复检测结果的导入格式。
- 外部诊断的 ID 加入工具来源，去重而不丢失来源；不因导入结果而声称执行过 lint。先支持导入已有结果，不自动启动项目命令。复用第一批任务生成器，为新类型补充 schema、排序与基线/对比测试。
- **C10 图与代码一致性检查**：新增 info 级别的一致性 finding，只使用现有数据（组件 `sources`、模块图、import 边、图上连线）：模块被多个组件认领、组件之间有真实 import 但图上没有连线、图上有连线但没有对应 import、模块不在图上。图上有线而无 import 时注明可能是静态分析看不到的运行时依赖；这些 finding 不参与严重级别排序，不作为 `--fail-on` 的默认触发条件。

### Codex 的具体任务

- **U8 类别与来源**：总览提供规范、复杂度、依赖/边界、一致性筛选及文件/函数搜索；规范问题显示工具和规则来源，使用项目实际诊断说明。
- **U9（基础版）**：问题按组展示并分页，避免 lint 结果一次全部渲染。
- **U13 一致性提示展示**：一致性问题与代码问题分开展示，文案明确“图与代码不一致”而非“代码有问题”。

### 门槛 G2

在 archify（ESLint）与 AI Voice（Ruff）上导入真实结果；每条可追溯到原工具和规则；未导入时显示“未检查”；一条规范问题完成导出 → 修改 → 重分析；一致性提示在至少一个真实仓库上抽查误报。

## 8. 阶段 3：重复代码

目标：回答“哪里写了两遍”。原第二批的 C6 / U7 / U9 移到本阶段，并先做校准。

### Claude 的具体任务

- **C6a 校准**：用现成的 token 级重复检测工具（如 jscpd）在 3 个以上真实仓库运行，结果按 C7 格式导入；人工抽查误报，确定最小 token / 有效行门槛与排除规则（生成、第三方、测试 fixture）。记录误报、漏报与限制。
- **C6b 决定实现方式**：若外部工具的位置信息足以支持稳定组 ID 和多位置证据哈希，则沿用并评估依赖体积与许可证（`THIRD_PARTY_NOTICES.md`）；否则按原计划自写保留标识符和字面量的 token 级检测，复用现有 Python/TS 提取器。决定与依据写入本文件。
- **C6c 重复组契约**：重复组稳定 ID 与多位置证据哈希；验证新增位置、删除位置及无关代码变化时的行为；输出完整位置列表、区间及可核对的重复规模。暂不做模糊语义相似和自动合并。复用任务生成器使重复组可导出。

### Codex 的具体任务

- **U7 重复对照**：两个位置默认对照，其他位置按需展开；明确共同片段和位置，保留跳转源码；窄屏上下排列，不强制横向双栏。
- **U9（完整版）**：重复组与大量问题的渐进加载；不一次渲染所有完整代码。导出先支持单项，少量相关问题批量选择在单项体验稳定后加入。

### 门槛 G3

真实重复可在两个位置直接核对，排除与门槛可解释；抽查记录包含误报、遗漏与限制，不以命中数量证明效果；一组真实重复完成导出 → AI 合并 → 行为对照 → 重分析。

## 9. 阶段 4：修改后验证

Claude负责：任务证据重新校验、基于文件反向依赖的可能影响范围、验证回执格式（不只记录退出码，需有测试汇总；AI Voice 案例中退出码 0 但无汇总即为反例）、可比较的重分析结果。对比规则/覆盖改变、解析失败、源码改名等情况时，不将“不再出现”直接认定为修复。项目命令执行与修改应用另行定义受控边界，初期复用编码 Agent 的正常工作流。

Codex负责：展示 AI 修改的外部 diff/验证回执入口、验证成功/失败/未执行状态，以及原问题仍存在、新增、不再检测到、不可比较的清晰区别。未建立实际集成前不展示可点击但无效的“自动修复”按钮。

### 门槛 G4

至少一个真实问题在页面上完成发现、导出、编码 AI 修改、审阅 diff、相关验证到重分析的完整案例。问题减少与行为测试通过分别展示；没有验证回执不得显示“优化已验证”。达到后按 G0 约定的条件推进合入 `dev`。

## 10. 协作顺序与交接材料

1. 阶段 0：Claude 实施 C0；整合者同时更新 #998 证据并与维护者对齐。
2. 阶段 1：Codex 先做 U10 拆分；Claude 同时实施 C8/C9 并提供 fixture；拆分合入后 Codex 实施 U11，再进行页面路径案例与 U12 试用。
3. 阶段 2：Claude 先交付 C7 格式草案与 fixture，Codex 据此实施 U8/U9 基础版；C10 与 U13 随后进行。
4. 阶段 3：C6a 校准结论确定后再实施 C6b/C6c 与 U7/U9 完整版。
5. 阶段 4：前几个阶段稳定后交付，不为等待完整影响分析而推迟单项任务导出。
6. 每个阶段结束同步一次最新 `dev`。

每次交接附：基线与候选提交、改动文件、字段或行为变化、测试命令与实际结果、示例结果、未解决事项。Claude另外提供引擎/契约 fixture；Codex另外提供截图、视口及浏览器检查结果。发现跨职责问题先记录具体输入与证据，再交给对应负责人修改。

不默认另开聊天或向 Claude 发送消息；本文件是可直接交给 Claude 的实施说明。实际启动开发时沿用用户指定的协作方式。

## 11. 验证与完成标准

- Claude：执行受影响的引擎/契约/CLI 测试；共享行为改动按 CONTRIBUTING.md 扩大覆盖，保留真实测试结果。
- Codex：执行受影响的 Code Analysis Chrome 浏览器回归，人工检查当前版本截图和交互；自动化通过与视觉验收分别记录。
- 整合者：核对新鲜度与兼容性，按仓库规则生成实际受影响的产物，检查最终组合提交。未刷新远端或未跑全套时如实标注，不报告合并就绪。
- 产品试用（阶段 1 起）：请未参与开发的用户尝试在 30 秒内指出优先位置及理由、60 秒内找到证据并导出任务；记录实际表现，未达到时由 Codex调整 UI。

完成的定义是用户能找到具体优化候选并交给 AI，随后能区分已验证结果与未完成验证。不得以功能清单、告警数量或测试通过替代真实流程验收。

## 12. 明确暂缓

综合质量分、完整任务管理平台、自动批量改代码、自动删除未使用代码、模糊业务语义重复、跨语言调用图、多语言合并报告和双语 UI。

一键发送到编码 AI 的适配器（[AI 交接设计](code-analysis-ai-handoff-design.md)中的 `/handoff` 接口）后置到阶段 4 之后，按试用反馈决定是否实现；实现时先只支持 `prepared` / `sent` 两个状态。

开发和测试不包含 live Archify 安装、更新或替换；不改变已发布版本与分发身份。
